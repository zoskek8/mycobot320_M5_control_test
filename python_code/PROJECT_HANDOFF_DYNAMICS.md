## 1. 무엇을 만들려는가

**목표**: 토크 센서 없이(인코더와 서보 피드백만으로) 주행 중 충돌을 감지하고,
감지되면 그 방향을 피해 경로를 수정한다.

논문 제목 후보:
- *Jacobian-informed Encoder-Only Collision & Reactive Avoidance for a 6DOF Manipulator*
- *Kinematics-informed Data-Driven Collision Detection and Reactive Avoidance
  for Sensor-Limited Robotic Manipulators*

### 1.1 원리

동역학 모델은 이렇다:

```
M(q)q̈ + C(q,q̇)q̇ + g(q) = τ
  ↑        ↑         ↑
가속에    움직여서   중력을
필요한    생기는     버티는
힘        힘         힘
```

데이터로 이 식을 식별하면, 현재 상태에서 **예상 모터 입력 τ̂**을 계산할 수
있다. 실제와의 차이가 residual이다:

```
τ_e = τ - τ̂
```

외력이 없으면 τ_e ≈ 0이고, 무언가에 부딪히면 τ_e가 튄다. 그리고 야코비안으로
그 토크가 손끝에서 어떤 힘이었는지 역산한다:

```
τ = Jᵀ F      →      F_ext = J⁻ᵀ τ_e
```

**주의**: 계획 메모에 `F_ext = Jᵀ τ_ext`로 적혀 있는데 `J⁻ᵀ`(실제로는
의사역행렬)가 맞다. 코드로 옮길 때 틀리기 쉬운 지점.

이걸로 "어느 방향으로 얼마나 밀렸는지"를 알면 그만큼 경로를 수정할 수 있다.

### 1.2 데이터 형식

MATLAB 등에서 바로 쓸 수 있도록 **수치 표(CSV)**로 뽑는다. 이미지가 아니다.

```
time | q1..q6 | q̇1..q̇6 | q̈1..q̈6 | u1..u6
```

## 2. [해결됨] u를 무엇으로 할 것인가 - 전류가 아니라 **부하**

계획 1단계가 "자세를 고정하고 u2를 측정"인데, 이건 버티는 데 드는 토크를
읽는다는 뜻이다. **읽을 수 있는지부터 확인해야 T1~T12 표의 u 열을 채울 수
있으므로**, 데이터 수집 전에 `mycobot_current_probe.py`로 먼저 가렸다.

### 2.1 서보 레지스터 지도 - 실측으로 확정

`get_servo_data(관절id, 주소)`로 서보 레지스터를 직접 읽을 수 있다. 주소
배치는 Feetech STS 계열 표준과 일치하는 것으로 **실측 3건으로 확정**:

| 주소 | 의미 | 확정 근거 |
|---|---|---|
| 56~59 | Present Position / Speed | 부하에 반응하는 자리 |
| **60** | **Present Load 하위바이트** | 아래 §3 곡선이 중력과 일치 |
| **61** | **Present Load 상위바이트(방향비트 포함)** | raw 293 관측(§3.2) |
| 62 | Present Voltage | 읽은 값 234.x ↔ 실제 전압 23.4V |
| 63 | Present Temperature | 읽은 값 26 ↔ `get_servo_temps()`의 J2 = 26 |
| **69** | **Present Current** | `get_servo_currents()`와 전 자세에서 일치 |

### 2.2 전류는 쓸 수 없다

`get_servo_currents()`는 존재하고 주소 69를 읽는다. **그런데 해상도가
못 쓸 수준이다**:

- 값이 **0 / 4 / 8.4 / 12** 뿐 - 4단위로 양자화돼 있다.
- J2를 -60°~+60°로 훑은 전 구간에서 범위가 **0~12**.
- 9개 자세 중 **4개가 정확히 0**으로 읽혔다.

이 해상도로는 `g(q)`를 매핑할 수 없다.

### 2.3 대신 Present Load(주소 60/61)를 u의 대리값으로 쓴다

같은 스윕에서 범위가 **8~293**으로 전류의 20배 이상이고, §3에서 보듯
중력 곡선을 R²=0.996으로 재현한다.

**2바이트로 읽어야 한다.** Present Load는 하위 10비트가 크기, 비트10이
방향이다. 하위 바이트만 읽으면 (a) 255를 넘을 때 값이 돌아가고 (b) 방향을
잃는다. 실제로 -60°에서 raw 293(= L 37 + H 1)이 관측됐다 - 하위만 읽었으면
**37로 보였을 값이다.** 분해 코드는 `mycobot_gravity_map.py:decode_load()`.

### 2.4 읽기 속도 - 60ms가 바닥, 우회 불가

| 항목 | 실측 |
|---|---|
| `get_angles()` | 30.0 ms (33.3 Hz) |
| `get_servo_data(부하)` | 30.0 ms (33.3 Hz) |
| 둘 다 매 사이클 | **60.1 ms (16.6 Hz)** |

**프레임 직접 조립 우회는 효과가 없었다.** pymycobot이 내보내는 요청 바이트를
가로채(`fe fe 04 53 02 3c fa`) 그대로 재전송하는 방식으로 시도했고, 값은
정확히 일치했지만(96 vs 96) **속도도 30.0ms로 동일**했다. 이전 프로젝트에서
`send_angles()`의 30ms를 0.4ms로 줄였던 것과는 성격이 다르다 - 쓰기는
라이브러리 지연이었지만 **읽기는 로봇 응답을 기다리는 펌웨어 왕복**이라
줄일 여지가 없다(§45의 33Hz 한계와 같은 벽).

**결론**: 주행 중 q와 u를 매 사이클 함께 기록하려면 **주기가 60ms(16.6Hz)**가
된다. 이전 프로젝트의 48ms보다 느리다. T7~T12를 설계할 때 이 제약을 전제로
해야 한다.

## 3. [완료] J2 정적 중력 매핑 - 계획 1단계

`mycobot_gravity_map.py --joint 2` (-60°~+60°, 15° 간격, **양방향** 스윕)

### 3.1 결과 - 중력 곡선이 그대로 나왔다

방향 비트를 살린 부호 있는 부하를, 양방향 평균으로:

```
부하 = -123.9 · sin(J2) + 2.9        R² = 0.9961
```

상수항 2.9는 사실상 0. **계획 1단계가 첫 관절에서 성공했다.**

| J2(도) | up | down | 양방향 평균 |
|---|---|---|---|
| -60 | +293 ※ | +96 | (194.5) |
| -45 | +112 | +72 | +92.0 |
| -30 | +72 | +56 | +64.0 |
| -15 | +40 | +32 | +36.0 |
| 0 | +8 | 0 | +4.0 |
| +15 | -32 | -32 | -32.0 |
| +30 | -48 | -72 | -60.0 |
| +45 | -80 | -104 | -92.0 |
| +60 | -96 | -96 | -96.0 |

※ -60° up의 293은 **스윕의 첫 측정**이고 온도가 23°C로 나머지(31°C)와
달랐다 - 냉간/정착 미완으로 보이는 일시적 값이다. down에서 같은 자세가
96이다. **앞으로 스윕 전에 워밍업 이동을 한 번 넣을 것.** 위 적합에서는
제외했다.

### 3.2 부호를 살리지 않으면 모양이 틀린다

1차 스윕(단방향, 하위바이트만)에서는 "J2=0에서 최소인 V자"로 보였고
좌우 비대칭(-45:112 vs +45:72)이 있어 원인을 찾고 있었다. **방향 비트를
반영하니 V자가 아니라 단조 감소 곡선**이고 비대칭도 사라진다. 크기만
보면 안 된다.

### 3.3 [중요] 마찰 이력이 실재한다 - 계획 식에 마찰항이 빠져 있다

같은 각도를 올라가며/내려오며 잰 차이:

```
+40, +16, +8, +8, 0, +24, +24, 0     (평균 +15, 전부 같은 부호)
```

**부호가 한쪽으로만 치우친다.** 이동 방향과 반대로 일정 크기로 작용하는
쿨롱 마찰의 전형이다. 그래서 **양방향 평균을 내면 상쇄되고**, 실제로
상쇄한 뒤 R²가 0.9961까지 올라갔다.

§1.1의 식 `M q̈ + C q̇ + g = τ`에는 마찰이 없다. 감속기가 있는 서보에서
쿨롱+점성 마찰은 코리올리항보다 큰 경우가 흔하고, 빼놓고 식별하면
**residual이 마찰로 가득 차서 충돌 없이도 튄다**(오검출). 식을 이렇게
확장해야 한다:

```
M(q)q̈ + C(q,q̇)q̇ + g(q) + F_c·sign(q̇) + F_v·q̇ = τ
```

이전 프로젝트 §48에서 "같은 자세인데 접근 방향에 따라 오차가 다르다"고
관측했던 것도 같은 현상이다.

### 3.4 규약: 정적 측정은 반드시 양방향 평균

위 결과로 확정한다. 단방향 스윕 값은 마찰 이력만큼 치우쳐 있다.

### 3.5 [방식 교체] 관절별 스윕 표로는 중력을 표현할 수 없다

**문제**: §3.1의 `부하 = -123.9*sin(q2)` 는 **q3=q4=q5=0 일 때의 단면
하나**다. J2에 걸리는 중력 토크는 J2 바깥 링크들의 무게중심 위치로
정해지고, 그 위치는 q3/q4/q5가 바꾼다. q3를 60도 접으면 팔이 짧아진
셈이라 진폭이 줄어든다. 6축 조합을 표로 채우려면 경우의 수가 수십만 개다.

**그러나 표로 만들 이유가 없다.** 중력 토크는 링크 질량과 무게중심
위치에 대해 선형이다:

    U(q) = Σ_i  m_i * g · (p_i(q) + R_i(q) c_i)
    τ_g  = ∂U/∂q = Y(q) · φ ,   φ_i = [m_i, m_i*c_ix, m_i*c_iy, m_i*c_iz]

(barycentric 파라미터). 즉 **자세 몇십 개만 재서 φ 를 풀면 그 뒤로는
어떤 자세든 계산으로 나온다.** 표가 아니라 파라미터를 구한다.

§3.1의 결과는 버리지 않는다 - q3=q4=0 단면에서 세 항이 모두 sin(q2)로
합쳐지므로 **식 하나**(`A+B+C = 123.9` 꼴)를 얻은 것이고, 식별이 끝난 뒤
그 단면을 예측해 대조하는 **검증용**으로 쓴다(`--verify`).

**Y(q)는 손으로 유도하지 않는다.** `τ_g2 = A sin(q2) + B sin(q2+q3) + …`
형태는 J2·J3·J4가 나란한 피치 축일 때만 맞다. 그 가정을 코드에 박는 대신
URDF 체인에서 **수치적으로** Y(q)를 만든다 - 축 배치가 무엇이든 맞고,
가정이 틀렸을 때 조용히 틀린 값을 내놓지 않는다. `--axes` 로 실제 축
배치를 먼저 확인할 수 있다.

**측정도 자세 단위로 바꾼다.** 자세 하나를 잡으면 J2·J3·J4·J5의 부하를
동시에 읽을 수 있어 한 번 이동에 네 관절 데이터가 나온다. 자세를 격자로
고르면 회귀 행렬이 쏠려 조건수가 나빠지므로 **무작위로** 뽑는다.
로봇을 움직이기 전에 `--dry` 로 조건수를 먼저 점검한다 - 수십 분 측정한
뒤에 "이 자세들로는 못 푼다"를 알면 늦다.

### 3.6 [실측] 축 배치와 식별 가능성

`--axes` 결과 (q=0 기준, base 좌표):

| 관절 | 회전축 | 중력 토크 |
|---|---|---|
| J1 | (0,0,+1) | **없음** - 베이스 회전축이라 **어떤 자세에서도** 수직. 측정 제외. |
| J2/J3/J4 | (0,-1,0) | 있음 (피치) |
| J5 | (0,0,+1) | **있음** - q=0 에서만 수직이다. 앞쪽 피치 관절이 움직이면 축이 기운다. **측정에 남긴다.** |
| J6 | (0,-1,0) | 있음 (피치) |

**주의**: `--axes` 는 q=0 단면만 본다. "축이 수직 -> 토크 0"은 J1에만
해당한다. J5를 같이 빼면 안 된다.

`--dry 40` 결과: 160행 x 24열, **유효 랭크 8**, **조건수 4.0**.

- 랭크 부족(8/24)은 정상이다. 중력만으로는 원래 식별되지 않는 φ 성분이
  있다(예: 회전축 방향 무게중심 성분은 중력 토크에 기여하지 않음).
  최소노름 해를 쓰고 **예측에만** 사용한다 - 개별 질량값에 물리적 의미를
  두지 않는다.
- **조건수 4.0은 매우 좋다.** 식별 가능한 부분공간 안에서는 파라미터가
  잘 정해진다는 뜻으로, 무작위 자세 전략이 통했다.
- 식별 가능한 방향의 개수를 **'축 개수 x 2' 같은 규칙으로 예측하지 말
  것.** 처음에 "피치축 4개 x 2 = 8"로 설명했는데 숫자가 우연히 맞은
  추측이었다 - 축 배치를 모사해 J6까지 측정에 넣으니 랭크가 10이 됐다
  (규칙대로면 12여야 한다). **어느 관절을 재느냐에 따라 달라지므로
  `--dry` 로 직접 잰다.**
- 위 결과에 따라 측정 대상을 `J2,J3,J4,J5` 에서 **`J2,J3,J4,J5,J6`** 로
  넓히고, 자세 생성에서 J6도 0 고정을 풀었다(고정하면 그 자세 성분이
  회귀에 안 들어가 해당 파라미터를 못 푼다).

**검증 완료(로봇 없이)**: 가짜 평면 체인에서 (a) 임의의 참 φ로 만든
토크를 다시 풀어 R²=1.0, (b) 수치미분이 6관절 전부 해석미분과 일치,
(c) 단일 질점에서 `m*g*L*cos` 해석해를 정확히 재현, (d) q2를 90도 접으면
τ1이 정확히 0으로 감(팔이 접히면 모멘트 팔이 사라짐 - **자세 의존성을
회귀행렬이 자동 처리한다는 증거**).

### 3.7 [중요] Present Load 는 물리적 토크가 아니다 - 관절별로 다뤄야 한다

§3.5에서 6축을 하나의 φ 로 묶어(barycentric 파라미터) 공동 식별했는데,
실측 32자세에서 이렇게 갈렸다:

| 방식 | J2 | J3 | J4 | 잔차 RMS |
|---|---|---|---|---|
| **관절별 독립 적합** | **0.998** | **0.996** | **0.982** | 2~3 |
| 파라미터 공유 강제 | 0.779 | 0.292 | 0.565 | 30 |

평면 사슬이면 바깥 링크의 무게가 안쪽 관절에도 그대로 실리므로 항이
**중첩**되어야 한다(τ4 의 항이 τ3 에, τ3 의 항이 τ2 에). 실측이 그
구조를 따르지 않는다는 것은 **Present Load 가 물리적 토크가 아니라는
뜻**이다. 서보 내부 PWM 듀티 계열 지표라 관절마다 감속비·마찰·제어이득이
섞인 **미지의 배율**이 붙는다.

**관절별로 보면 그 배율이 계수에 흡수되므로 문제가 없다.** §3.1의 J2 스윕이
R²=0.996 으로 예쁘게 나왔던 것도 같은 이유다 - 한 관절만 보면 잘 맞는다.

**교수님 계획은 처음부터 관절별이었다.** 1단계가 "다른 관절 고정하고 u2
기록", 3단계가 `u2 = f(q2, q3)`, 4단계 표가 u1~u6 각 열이다. u 들을 하나의
공유 모델로 묶으라는 요구는 어디에도 없다. §3.5에서 공동 식별로 바꾼 것은
"자세마다 부하가 다른데 표가 무슨 의미냐"는 지적에 대한 대응이었는데,
**그 지적은 관절별 방식 안에서도 풀린다** - 표 대신 관절별 함수를 쓰면 된다.

### 3.8 [완료] 관절별 중력 모델 - 계획 1~3단계

무작위 자세 40개(도달 32개)로 관절별 식별:

| 관절 | 부하 표준편차 | 잔차 RMS | R² |
|---|---|---|---|
| J2 | 64.6 | 2.7 | **0.998** |
| J3 | 35.5 | 2.3 | **0.996** |
| J4 | 13.3 | 1.8 | **0.982** |
| J5 | 4.0 | 3.2 | 0.376 |
| J6 | 1.7 | 1.8 | -0.143 |

잔차 RMS 2~3 은 **측정 불확실도와 같은 크기**다(§3.9). 더 줄일 여지가 없다.

J5/J6 는 부하 표준편차가 4.0 / 1.7 로 신호 자체가 데드밴드에 묻혀 있다.
손끝에 질량을 달면 값이 커지므로 그때 다시 볼 것.

**계획 3단계(커플링)는 이 안에 이미 들어 있다.** 회귀행렬 Y(q) 의 j 행은
그 관절 바깥 링크의 자세를 전부 포함하므로 "q3 를 접으면 q2 부하가 준다"가
자동으로 반영된다. q3 를 0/30/60 에 고정해 눈으로 확인하는 절차는 검증용으로
따로 해도 좋다.

계수는 `gravity_params.json` 에 저장된다.

### 3.9 측정 불확실도 - 접근 방향 편차는 잡음이 아니라 계통 성분

도달한 32자세에서 두 접근 방향 값의 관계:

| 관절 | up-dn 상관 | 방향성분 (up-dn)/2 평균 | 그 표준편차 |
|---|---|---|---|
| J2 | +0.977 | **-9.7** | 7.0 |
| J3 | +0.992 | +1.8 | 2.3 |
| J4 | +0.961 | -1.3 | 1.9 |

상관이 0.96~0.99 로 두 값이 거의 같이 움직인다. 차이는 **쿨롱 마찰에 의한
계통 오프셋**(J2 에서 -9.7)이고 **양방향 평균으로 상쇄된다**(§3.4 규약이
옳았다). 따라서 평균값의 불확실도는 2~7 수준이다.

**주의**: `dir_spread` 열은 5개 관절의 최댓값이라 J2 의 방향 오프셋에
지배된다. 이 값(평균 21)을 잡음으로 읽으면 불확실도를 3배쯤 과대평가하게
된다 - 실제로 한 번 그렇게 오판했다.

## 4. 앞으로 할 일

### 4.1 남은 정적 측정 - **계획 1~3단계는 완료됨**(§3.8)

J2/J3/J4 는 R²=0.98~0.998 로 끝났다. 남은 것:

1. **J5/J6** - 지금은 신호가 데드밴드에 묻혀 있다. 손끝에 알려진 질량을
   달아 부하를 키운 뒤 재측정한다. 이 측정은 **N·m 환산 계수**도 같이
   준다(§4.3의 야코비안에 필요).
2. **(선택) 커플링 눈으로 확인** - 계획 3단계 원형대로 q3 를 0/30/60 에
   고정하고 q2 스윕. `mycobot_gravity_map.py --joint 2 --hold 0,0,30,0,0,0`.
   §3.8 모델이 이미 담고 있으므로 필수는 아니고 확인용이다.
3. **자세 범위 보강** - §3.1 스윕 단면(다른 관절 전부 0, 완전히 뻗은 자세)은
   무작위 자세 집합에서 보면 바깥쪽 조건이다. 그 영역 자세를 몇 개 더 넣어
   재적합하면 외삽이 줄어든다.

### 4.2 T1~T12 주행 데이터 수집 (계획 5단계)

순기구학 영역 - 관절을 직접 지령:
- **T1/T2/T3**: J1만 / J2만 / J3만 속도가 사인파. 나머지 고정.
- **T4**: J2+J3 동시 (정속, 가변속)
- **T5**: J2+J3+J4 동시
- **T6**: 6축 전체 point-to-point (가속-정속-감속)

역기구학 영역 - 엔드이펙터 경로:
- **T7**: 직선, trapezoidal 또는 S-curve 속도 프로파일
- **T8**: 원/곡선을 거의 정속으로
- **T9**: random waypoint, 다양한 가·감속
- **T10/T11/T12**: **같은 경로**를 느리게 / 중간 / 빠르게

**왜 이 구성인가**: `g(q)`는 속도와 무관하고, `C q̇`는 속도의 제곱에,
`M q̈`는 가속도에 비례한다. 정속 구간에서는 q̈≈0이라 중력+마찰만 남고,
가속 구간에서 관성항이 드러난다. T10~T12가 **같은 경로를 속도만 바꾸는**
이유가 이것이다 - 자세(=중력항)를 고정한 채 속도 의존 항만 변화시킨다.

**T1~T3에서 사인파를 쓰는 것의 이점**: 지령이 해석적 함수라 q̇, q̈를
미분 없이 수식으로 얻을 수 있다. 60ms 주기 데이터를 두 번 미분해서 q̈을
구하면 노이즈가 심한데, 이 방식은 그 문제를 우회한다. **T7 이후에도
가능하면 해석적으로 q̈을 아는 궤적을 쓰는 게 좋다.**

### 4.3 미해결/주의

- **q̈ 산출 방법 미정**. 16.6Hz 데이터의 이중 미분은 노이즈가 크다. 지령
  궤적에서 해석적으로 뽑을지, 측정값을 필터링해 쓸지 정해야 한다. 이전
  프로젝트 §46/§47에 각가속도 노이즈 제거 경험이 있으니 참고할 것.
- **반응 속도 상한**. 60ms 주기면 감지 지연이 최소 60ms + 필터 지연이다.
  35mm/s에서 약 2mm 이동에 해당한다. "reactive avoidance"의 성능 한계가
  여기서 정해진다.
- **Present Load의 물리 단위 미확인**. 지금은 서보 내부 단위의 숫자일 뿐
  N·m가 아니다. 야코비안으로 힘을 역산하려면(§1.1) 환산 계수가 필요하다.
  알려진 질량을 손끝에 매달아 재는 방법이 있다.
- **온도 상승**. 정지 상태로 중력을 버티면 서보가 계속 전류를 흘린다.
  스윕 중 23→31°C로 올랐다. 긴 측정에서는 55°C 상한 감시가 작동하는지
  확인할 것.

## 5. [진행 중] T1~T12 주행 데이터 수집 - 계획 5단계

`mycobot_traj_collect.py`. 출력은 계획 형식 그대로:
`time | q1..q6 | qd1..qd6 | qdd1..qdd6 | u1..u6` (+ `q*_cmd`, `track_err`, `dt`, `dq`).

### 5.1 궤적 형태 - 세 번 고쳐서 자리잡았다

| 시도 | 식 | 문제 |
|---|---|---|
| 1차 | `q̇ = V·sin(ωt)` | 반주기마다 **부호가 뒤집혀** 위치가 왕복. 방향 전환마다 쿨롱 마찰 부호가 뒤집히고(§3.9의 -9.7) 속도 0 에서 정지마찰·백래시가 낀다 |
| 2차 | `q̇ = V₀(1-cos ωt)` | 방향 전환은 없으나 **매 주기 속도가 정확히 0** 을 찍어 정지마찰이 다시 낀다 |
| **현재** | **`q̇ = v₀ + v₁·sin(ωt)`, v₁=ratio·v₀, ratio<1** | 속도가 항상 양수. 한 방향으로만 돌고 마찰이 상수 오프셋으로만 남는다 |

계획서 그래프도 0 을 가로지르는 사인이 아니라 **가로선 주위에서 물결치는
곡선**이다("정속, 개변"). `q̇`, `q̈` 는 해석적으로 알 수 있어 60ms 데이터를
두 번 미분하는 노이즈를 피한다.

**360도 연속 회전은 불가능하다** - J1 ±165, J2 ±135 등 한계가 있다.
시작점은 주행 구간이 범위 가운데 오도록 자동 배치된다(`--start` 로 지정 가능).

### 5.2 u 는 **전류**로 읽는다 - 부하는 주행 중에 쓸 수 없다

`--source load`(관절당 Present Load 2바이트)로 주행 데이터를 받아보니
u 값이 **-1023 ~ +1023** 에 걸쳐 나왔다(정지 측정에서는 8~112 였다).
**하위/상위 바이트를 별도 호출로 읽는데 그 사이 30ms 가 지나기 때문**이다.
정지 상태에서는 값이 안 변해 문제가 없었지만, 주행 중에는 서로 다른 시각의
두 바이트를 합치게 되어 상위바이트가 어긋나면 수백씩 튀고 방향 비트까지
뒤집힌다. **2바이트 읽기는 원자적이지 않다.**

`get_servo_currents()` 는 **6축을 한 번의 호출(30ms)로** 읽으므로 이 문제가
없고, 루프도 빠르다. 다중 패스도 불필요해진다.

| 방식 | 주기 | 속도 사인 R² |
|---|---|---|
| u 안 읽음 | 37±3ms | 0.978 |
| **전류** | **66±2ms** | **0.994** |
| 부하(1관절) | 130±73ms | 0.456 |

부하 읽기가 루프를 130±73ms 로 불규칙하게 만들면, 로봇이 지령 간격을 30ms
만에 주파하고 100ms 를 멈춰 서는 **가다-서다**가 되어 속도 파형이 깨졌다.
(각도 읽기 정체는 원인이 아니었다 - 정체율 2%.)

**send_angles 의 speed 도 낮춰야 한다.** 100 이면 로봇이 먼저 도착해 멈춰
선다. 지령 최대 속도의 1.2배로 자동 설정한다.

### 5.3 [중요] 자세 범위를 넓게 훑어야 한다 - 좁으면 신호가 죽는다

J2 에서 자세 범위만 바꿔 실측한 u2 분포:

| 구간 | 폭 | u2 표준편차 | 서로 다른 값 |
|---|---|---|---|
| -33 ~ +32도 | 64도 | 4.03 | 14개 |
| +40 ~ +104도 | 64도 | **1.66** | 8개 |
| **-70 ~ +71도** | **141도** | **12.91** | **44개** |

**중력이 큰 곳이 아니라 중력이 많이 변하는 곳이 필요하다.** +40~104도는
sin(q2) 가 0.64~0.97 로 거의 평평해 신호가 오히려 줄었다. -70~+71도는
sin 이 -0.94~+0.95 로 전 범위를 훑는다.

이는 §0.1 의 작업 규약("좁은 범위에서 잰 값으로 일반화하지 않는다")과
같은 이야기이고, 교수님 계획 1단계도 원래 "q2 를 -60,-45,…,60 으로 훑어라"
였다. **T1~T12 전부 관절의 안전한 도달 범위 전체를 훑는다.**

### 5.4 책상 충돌 - 관절 한계만으로는 부족하다

J2 를 -125도(한계 ±135 안)로 돌렸다가 **바닥을 박았다.** 팔이 뒤로 누우면
손끝이 바닥에 닿는다. J1 은 회전축이 수직이라 문제가 없었지만 J2/J3 는 눕는다.

이제 실행 전에 궤적 전체를 FK 로 훑어 **책상 충돌과 자가충돌**을 검사하고,
걸리면 안전 구간과 함께 다시 쓸 명령을 알려준다. `--safe-range` 로 그
관절의 안전 각도 구간만 따로 볼 수도 있다(로봇 불필요).

**손끝만 보면 부족하다.** 처음엔 TCP 높이만 검사했는데, 팔을 접으면
팔꿈치나 손목이 손끝보다 먼저 바닥에 닿는다. J3 를 -140~+140도로 훑어보니
**9개 자세 중 7개에서 손끝보다 낮은 링크가 있었다**(J1/J4/J6 원점).
지금은 모든 링크 원점 높이를 본다.

**한계**: 링크 원점만 보고 부피는 고려하지 않는다(메시 충돌 검사가 아니다).
`DESK_SAFETY_MARGIN_MM` 여유를 남겨두고, **처음 도는 궤적은 눈으로 지켜볼 것.**

### 5.5 [필수] 회차 반복 - 한 번 재서는 안 된다

궤적이 제대로 도는지 확인하는 단계는 한 번으로 족하지만, **식별에 쓸
데이터는 반복해야 한다.** `--reps` (기본 4), 홀수 회차는 자동으로 반대
방향으로 돈다.

세 가지 이유:

1. **잡음 크기를 알아야 residual 문턱값을 정할 수 있다.** 한 번만 재면 지금
   u 값이 로봇의 성질인지 그 회차의 우연인지 구분할 수 없다. 회차간
   표준편차가 곧 잡음 크기이고, 충돌 판정 문턱은 이보다 커야 한다.
   **이 프로젝트의 최종 목표가 residual 로 충돌을 잡는 것이므로 필수다.**
2. **마찰 오프셋이 파라미터에 섞이는 것을 막는다.** 단방향으로만 돌면
   쿨롱 마찰이 상수로 깔려 들어간다. 정방향 평균과 역방향 평균의 차이가
   마찰의 2배이고, 둘을 함께 쓰면 상쇄된다(§3.4 규약과 같은 이유).
3. **전류 양자화를 완화한다.** u 가 4단위로 끊기는데, 회차마다 양자화
   경계를 지나는 시점이 조금씩 달라 평균하면 중간값이 복원된다.

`repeatability_report()` 가 u 를 **시간이 아니라 각도의 함수로** 비교한다 -
역방향 회차는 같은 각도를 반대 순서로 지나므로 시간축으로는 못 맞춘다.
검증: 중력 20·sin(q) + 마찰 ±3 + 잡음 1.0 을 심은 합성 데이터에서 방향
차이 6.04(참값 6.0)로 복원.

CSV 에 `rep`, `dir` 열이 추가되며 전 회차가 한 파일에 쌓인다.

### 5.6 결과 요약과 남은 문제

| 실험 | 자세 범위 | 속도 사인 R² | 추종오차(지연보정후) | u 표준편차 |
|---|---|---|---|---|
| T1 (J1) | 270도 | 0.994 | 0.25도 | u1 = 2.09 |
| T2 (J2) | 141도 | 0.980 | 1.25도 | u2 = **12.91** |
| T3 (J3) | 272도 | 0.991 | 0.81도 | u3 = 3.48 |

**위는 전부 1회차 결과다.** §5.5 에 따라 `--reps 4` 로 다시 뽑아야 한다.

**T1 의 u1 이 약하다.** J1 은 회전축이 수직이라 중력이 안 걸리고 관성·마찰만
남는데, 그 토크가 전류 해상도(4단위) 아래에 묻힌다. 가속도를 2.7배 올려도
표준편차가 2.09→2.60 에 그쳤다 - **T1 은 이것이 한계로 보인다.**

**커플링 신호도 약하다.** T2 에서 J2 가 움직이면 J3 에도 반력이 걸려야 하는데
u3 가 0~3 뿐이다. 동역학의 커플링 항을 잡으려면 이게 필요하다.

**질량을 매달아 해결하려 해서는 안 된다.** 한때 그 방향을 제안했으나
틀렸다 - 질량을 단 채로 식별하면 **그 질량이 달린 로봇의 파라미터**가
나온다. 떼면 안 맞고, 무게가 바뀔 때마다 달라진다. 충돌 감지는 평소
상태의 로봇에서 작동해야 하므로 측정 조건과 사용 조건이 같아야 한다.
질량은 **N·m 환산 계수(서보 자체의 비례 상수)를 구할 때만** 쓴다.

u3 커플링이 약한 것은 T4(J2+J3 **동시**)를 해봐야 실제 문제인지 알 수
있다. T3 는 J3 만 움직이고 J2 는 정지였다.
